# Тестовое задание — Snapbuild

Развитие продуктового лендинга [снэпбилд](https://snapbuild.ru/): существующие блоки страницы дополнены пятью новыми полноценными секциями. Проект собран как единый адаптивный лендинг на React и опубликован на GitHub Pages.

## Опубликованная версия

[https://lina-gritsel.github.io/snapbuild-task/](https://lina-gritsel.github.io/snapbuild-task/)

## Локальный запуск

Требуется Node.js 24 или новее.

```bash
npm install
npm run dev
```

После запуска страница доступна по адресу, который выведет Vite (обычно `http://localhost:5173`).

## Использованный стек

- React 19, TypeScript и Vite;
- CSS с дизайн-токенами и адаптивными правилами без стороннего UI-kit;
- ESLint и Prettier для единых правил качества кода;
- GitHub Actions и GitHub Pages для сборки и публикации.

## Пять добавленных секций

1. **Как заявка превращается в результат** — последовательность работы с задачей и результатом.
2. **Из брифа в готовые материалы** — сценарий подготовки материалов для команды.
3. **Отзывы** — реальные по структуре карточки с ролями, компаниями и результатами.
4. **Тарифы** — варианты подключения с возможностями и CTA.
5. **Форма обратной связи** — кастомный список тем, валидация обязательных полей, согласие с политикой и отправка подготовленного письма через почтовое приложение.

## Как анализировалась стилистика исходного сайта

За основу взяты визуальные паттерны исходного лендинга: крупная типографика, тёмный текст на светлом фоне, большой радиус карточек, аккуратная сетка, градиентные CTA, спокойные серые границы и плавные микроанимации. Новые блоки используют те же размеры отступов, цветовые токены, форму кнопок и принципы адаптивной перестройки, поэтому продолжают страницу, а не выглядят отдельным шаблоном.

## Что удалось воспроизвести

В проекте собраны основные части исходной страницы: шапка, первый экран, логотипы, блоки о продукте и преимуществах, безопасность, дорожная карта, FAQ, финальный CTA и подвал. Между ними встроены пять новых секций, чтобы сохранить цельный сценарий знакомства с продуктом.

## Что не реализовано

Форма не отправляет данные на сервер и не хранит их: по условию задания для неё не требуется backend. Вместо этого она проверяет обязательные поля и открывает письмо с заполненными данными в почтовом приложении пользователя.

## Что можно улучшить при дополнительном времени

- Добавить интеграцию формы с серверным API и состояние успешной отправки внутри интерфейса.
- Дополнить проект e2e-тестами интерактивных сценариев и проверками доступности.
- Подключить аналитику и оптимизировать изображения под разные плотности экранов.

## Использование AI-инструментов

Для ускорения рутинных задач использовался Codex: анализ структуры проекта, миграция на TypeScript, настройка ESLint и Prettier, реорганизация компонентов и повторная проверка сборки. Все изменения были проверены вручную через локальный запуск, линтер, проверку типов и production-сборку.

## Проверки качества

```bash
npm run format:check
npm run lint
npm run typecheck
npm run build
```

## Структура проекта

- `src/layout` — каркас страницы: шапка и подвал.
- `src/sections` — самостоятельные секции лендинга; данные, локальные хуки и стили лежат рядом с владельцем.
- `src/shared` — переиспользуемые UI-компоненты, конфигурация и браузерные утилиты без зависимости от секций.
- `src/styles` — глобальные токены, шрифты, базовая раскладка и общие правила адаптивности.
- `public/assets` — изображения, шрифты и другие статические ресурсы.

Публикация выполняется автоматически через GitHub Actions при каждом push в `master`.
